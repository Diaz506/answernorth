# Functions backend

The nine existing UDF signatures are preserved, with additional UDFs for run drafts, plan approval, a hard-disabled start operation, and read-only job status. The backend requires four deployment-specific settings on every invocation: `ANSWERNORTH_TENANT_ID`, `ANSWERNORTH_WORKSPACE_ID`, `ANSWERNORTH_APP_ID`, and `ANSWERNORTH_OWNER_ID`. Each must be a valid RFC-variant UUID. They are read once per invocation through the Rayfin context secret API; no defaults or committed resource values are supplied. Missing or invalid settings return `CONFIGURATION_ERROR` before any database or network access. Validation rejects one common placeholder but cannot distinguish every invented UUID from a real one; the operator must verify each configured identifier. Set the owner to the canonical authenticated user identifier, not an arbitrary viewer or service identity.

The installed Rayfin SDK checks the per-invocation secret bag before falling back to local environment values. `ctx.getSecret` is deprecated in favor of generated `ctx.Secrets`, but remains documented for names not yet registered and allows a fresh clone to build before provisioning. Never hand-edit the generated registry. See the [deployment guide](../../../docs/CONFIGURATION.md) for masked secret setup and acceptance checks. One isolated deployment confirmed that the revised managed-subject binding and resource-token checks admit the configured owner; a different authenticated identity and direct data paths have not yet been verified.

The host authenticates the caller token signature. The backend checks the injected Fabric token's expiry, tenant, fixed audience and object ID against the configured owner, as well as the caller's canonical owner. Only the configured application owner may invoke these functions. The hosted Fabric token uses **application owner rights**, not viewer permissions or viewer RLS. Discovery lists accessible workspaces in that configured tenant; the configured application workspace is read explicitly. It does not establish agent publication, inference access, or evaluation readiness. Cross-user platform policy behavior must still be verified on a managed deployment.

Suites use owner-filtered reads and immutable owner-stamped writes; reload verifies row owner, structure, identifiers, and hashes. Hashes detect corruption, not malicious owner tampering or server attestation. Save uses case rows followed by a manifest and is not atomic; failed saves can leave invisible orphan rows, and no retry is automatic. Suite content is untrusted data. Empty or omitted category is allowed.

Run drafts and approval markers use create-only owner-scoped records. The request UUID makes identical draft creation idempotent and a changed snapshot conflicts. Approval binds the reviewed digest and requires revalidation of the saved suite and agent metadata, but does not check publication or authorize execution. An internal, unregistered coordinator can claim, submit once and record a validated job receipt; the public start UDF remains hard-disabled. Status reads require the receipt to match separately configured server-side notebook and workspace IDs. Prechecking recent jobs is not an atomic cross-run lock, so the coordinator is not ready to enable. Neither the digest nor these records are tamper-proof attestations.

Smoke submission, evidence, AI qualification and suggestions are permanently disabled stubs: they authenticate and validate scope, then return `FEATURE_DISABLED` without storage, network calls, or generated results. General evaluation execution is disabled. The optional agent probe only performs a bounded capability handshake against the fixed Fabric origin; it never sends a question or calls a tool.
